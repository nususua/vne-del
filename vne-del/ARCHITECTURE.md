# Архитектура · Вне дел

## Основной автономный режим

bootstrap.js последовательно загружает приложение. По умолчанию local.js подставляет автономный адаптер вместо сетевого API: никакие письма или запросы в Supabase не отправляются. Три профиля, проверочный код 1234. Это имитация авторизации, не способ защиты личных данных.

Основное хранилище localStorage: ключ vnedel-local-database-v1. Структура:

```json
{"version":1,"activeUser":"anna","profiles":[{"id":"anna","name":"Анна","city":"Москва","bio":"О себе"}],"boards":{"anna":{"interests":["Пение"],"saved":[15],"statuses":{"15":"В процессе"},"notes":{"15":"Спеть куплет"}}},"posts":[],"messages":[]}
```

posts содержит строки {id,user_id,data}, messages — {id,user_id,kind,target_id,body}. Доски адресуются по ID профиля; общие публикации и сообщения доступны всем трём профилям в одном браузере. Выход меняет activeUser на null и не удаляет доски. Восстановление читает хранилище заново, поэтому перезапуск сервера не сбрасывает данные. Очистка сайта и другой браузер означают отсутствие этих сохранений; владелец устройства может менять localStorage напрямую.

Сетевой режим выбирается только параметром ?mode=cloud; далее описана его дополнительная архитектура.


## Состав

Браузерное приложение без сборки: index.html, style.css, catalog.js, model.js, cloud.js, app.js. Bootstrap 5.3.3 расположен локально. START.command запускает статический сервер Python на 127.0.0.1:5174. Приложение обращается к Supabase Auth и PostgREST через HTTPS.

## Авторизация

Почта → запрос одноразовой ссылки → переход из письма → серверная проверка пользователя. Токены из фрагмента ссылки удаляются из адреса после получения. Сеанс хранится в localStorage под vnedel-cloud-session-v1; при истечении access token используется refresh token. Пользовательские права проверяются сервером, а не локальным полем session. Выход удаляет сеанс и локальное состояние приложения. Вход по коду предусмотрен в адаптере, но текущий интерфейс использует ссылку из штатного шаблона Supabase.

Публичные параметры — URL проекта и publishable key — в config.local.js, исключённом из Git и архива. config.example.js и .env.example содержат пустые значения. Secret/service_role ключей и пароля базы в приложении нет.

## Таблицы

| Таблица | Поля | Доступ |
| --- | --- | --- |
| profiles | id UUID → auth.users, name, city, bio | Публичное чтение, запись своего профиля |
| boards | user_id UUID, data JSONB, updated_at | Только владелец |
| posts | id, user_id → profiles, data JSONB, created_at | Публичное чтение, запись автора |
| messages | id UUID, user_id → profiles, kind, target_id, body, created_at | Публичное чтение, добавление от своего имени |

Схема и политики RLS: backend/schema.sql. Скрипт выполняется один раз целиком в транзакции. Почта доступна службе Auth и не включается в profiles. Приватные заметки никогда не записываются в публичные сообщения.

## JSON публикации

```json
{"id":"post-UUID","authorId":"UUID","title":"Песня на вечер","description":"Попробовать куплет","category":"Пение","city":"Москва","format":"home","price":0,"duration":20,"image":"assets/music.svg","materials":"Любимая песня","firstStep":"Выбрать удобную тональность"}
```

В серверной политике authorId должен совпадать с владельцем строки; отображаемое имя восстанавливается по профилю. Название до 90, описание до 1500, город до 50, материалы и первый шаг до 300 символов. Время 5–1440 минут, бюджет 0–1 000 000 ₽. Имя до 60, биография до 500, сообщение до 300 символов. Размер JSON доски до 100 КБ, публикации до 12 КБ ограничен БД.

## Сохранение и обновление

Локальный снимок vnedel-final-v1 изолирован от старого vnedel-v1. Сохранения доски и своих публикаций отправляются последовательно. Статус успеха появляется после ответа сервера; сбой отмечается с возможностью повторить. Комментарий добавляется в интерфейс после успешной записи. Лента загружается при открытии приложения и по кнопке обновления. Записи больше лимита выборки пока не подгружаются: до 500 публикаций и 1000 сообщений. Пагинация — дальнейшее развитие.

## Ограничения

Нужен интернет. Штатный SMTP Supabase ограничен участниками команды и малым числом писем; для свободной регистрации нужен собственный SMTP. Нет серверного ограничения частоты публикаций и модерации: для открытого публичного запуска их нужно добавить. Стартовые вымышленные профили не имеют аккаунтов. Проверка двух реальных аккаунтов обязательна перед заявлением о полностью проверенной изоляции данных.

## Доработка удобства

Общая выборка нормализуется до 500 публикаций; лимит 50 на новую публикацию проверяется для текущего автора, а не всей ленты. Сортировка не изменяет исходный каталог. Черновик новой публикации хранится в sessionStorage под отдельным ключом аккаунта. Несохранённая личная заметка восстанавливается при повторном открытии карточки в текущем сеансе. При удалении сохранения доступна отмена с восстановлением статуса и заметки. Успешный вход в другой вкладке обнаруживается через событие storage и проверяется сервером.
